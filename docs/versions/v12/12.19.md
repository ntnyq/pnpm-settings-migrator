# pnpm 12.19

Compared exact tags **12.18.0 → 12.19.0**, including the full configuration
source diff and release notes. Patch changes in this minor belong here with
their exact release boundaries.

## Added fields and nested values

From **12.19.0**, `projectScopedOptionalPeers` accepts a boolean or null.
When enabled, a missing optional peer must be supplied by that project's own
dependencies, or root dependencies when `resolvePeersFromWorkspaceRoot` is on.
Other projects can still influence version selection. The default is false;
`dedupePeerDependents: false` already implies project scoping. This is a workspace
policy, unavailable in `packageConfigs` or subproject configuration.

Also from **12.19.0**, the existing `lockfile` object accepts `format: v9` or
`format: v13`; null leaves v9 effective. v13 is an experimental output format,
not a pnpm major target. It uses JSON-like YAML with trailing commas, `projects`
instead of `importers`, and package entries that include peer bindings instead
of a separate snapshots section. Both formats can be read regardless of the
output setting. `includeResolutionSettings` and `integrityTarget` retain their
earlier introduction boundaries.

The migrator enables both additions only for a confirmed stable target of
12.19.0 or later on v12. Earlier, imprecise, prerelease, and unknown-major
targets retain the complete source setting, including sibling lockfile options.
Invalid nested values and unknown options retain the whole object. Existing
incompatible YAML fails before writes. Ordinary lockfile format placeholders
remain literal for pnpm to expand; the migrator never evaluates them. No
upstream defaults are inserted. Existing merge and conservative INI-section
cleanup rules remain unchanged.

## Reading and consumption changes

Project registry URLs containing environment placeholders now fail with
`ERR_PNPM_REGISTRY_ENV_NOT_EXPANDED`, rather than falling back to another
registry. This applies to project `.npmrc`, workspace YAML, and config-dependency
settings. Dynamic proxy, `pnprServer`, and `userAgent` values are ignored with
warnings. The migrator already retains these unsafe or ineffective values in
their sources; credential and machine-level protections remain unchanged.

The loaded linker now materializes packages requiring builds or filesystem
access automatically and can load approved builds from the side-effects cache.
`supportedArchitectures` also changes foreign-platform archive storage and
single-platform variant selection. Their accepted configuration shapes did not
change, so existing settings migrate unchanged. Workspace engine/platform checks,
hoisted/custom-module layout fixes, runtime reinstall behavior and Windows import
defaults require no new migration rules.
